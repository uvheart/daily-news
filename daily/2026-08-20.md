## 4. Agent / Coding Agent / Computer Use

### 4.1 LEGO-RL：不要重新实现一个“训练专用 Agent”，直接训练真实 Harness

**日期：2026-08-18。**

LEGO-RL 今天最值得看的一点，是它把现实中的 Coding Agent Harness 当成 training runtime，而不是为了 RL 重新写一个简化 agent loop。

它要解决三类真实工程问题：

1. **Train-Inference 一致性**：Harness 可能做 context compaction、message reserialization、tool message 变换，如果 trainer 使用的 token/logprob 与真实 rollout 不一致，policy-gradient 更新会失真。LEGO-RL 通过 in-process LLM proxy 抓原始 generation stream，再由 trainer 侧重算 log-prob。
2. **Sandbox 可靠执行**：大规模 repo task 会遇到环境 crash、image pull、依赖污染、reward hacking，需要 image cache、stage-wise validation 与独立执行边界。
3. **Trajectory 可观测性**：长 Agent rollout 出错时，单纯看 reward 无法定位问题，因此集成 validation、monitoring 和 Live UI。

论文在 Qwen3.5-35B-A3B 上使用 GSPO，并分别接 OpenHands SDK、Claude Code、OpenCode。作者报告 SWE-bench Verified 上三套 Harness 都有明显提升，同时 rollout-training probability correlation 保持在 0.99 以上。

来源：
- [arXiv：LEGO-RL](https://arxiv.org/abs/2608.17393)

### 4.2 Tool / MCP 安全：真正需要管的是“动作”，不只是“提示词”

**日期：2026-08-18。**

《When Agents Act on Web3》虽然以 Web3 为对象，但讨论的问题适用于任何能修改外部状态的 Agent：当 MCP/Skill/Tool 可以发请求、写数据库、转账、修改代码、删除资源时，攻击面变成 **权限 + action sequence + credential + external side effect**。

对 Agent Platform 的工程启示：Tool Registry 不应该只是“注册 name/schema”，还应该维护：

- tool origin / identity；
- read-only vs state-changing capability；
- scope / tenant / credential policy；
- sequence constraints；
- replay / idempotency；
- audit trace；
- high-risk action approval。

来源：
- [arXiv：When Agents Act on Web3](https://arxiv.org/abs/2608.17275)

## 5. Agentic RL / RL Infra

### 5.1 Agentic RL 的新矛盾：真实 Harness 与 Policy Gradient 怎么对齐？

**日期：2026-08-18。**

LEGO-RL 的意义可以用一句话概括：

> **Agentic RL 的 rollout 不再只是 model.generate()，而是一整个会重写上下文、调用工具、管理 workspace、压缩历史的 runtime。**

因此训练系统必须开始处理：

```text
Agent Harness
   ↓
LLM Proxy / Generation Capture
   ↓
Tool + Sandbox Interaction
   ↓
Trajectory
   ↓
Trainer-side Token / LogProb Reconstruction
   ↓
Policy Update
```

这会把很多过去属于“应用层”的东西拉进 RL Infra：context compaction、tool serialization、agent session state、sandbox status、retry、trajectory schema、reward provenance。

来源：
- [LEGO-RL](https://arxiv.org/abs/2608.17393)

### 5.2 FACA：Multi-turn RL 开始认真解决局部 Credit Assignment

**日期：2026-08-18。**

很多 Agent RL 系统仍然是：整条 trajectory 完成后给一个 0/1 或一个最终 score，然后所有 action 共享这个 outcome signal。这对长任务非常粗糙。

FACA 的思路是：用户下一轮 reaction 虽然噪声很大，但它通常包含对上一段 agent behavior 的局部反馈。例如 Agent 问了一个好问题，用户下一轮会更顺畅地提供必要信息；Agent 理解错了，用户可能立即纠正。FACA 把这种 reaction 转成 locally normalized advantage，再与 terminal verified outcome advantage 相加。

作者报告，与 outcome-only Interactive GRPO 对照相比，九领域平均结果在 8B 和 14B 模型上分别提升 5.91 和 10.22 个百分点，并在其他 benchmark 上保持同样趋势。

**Infra 启示：** trajectory 系统以后不能只保存 `(prompt, response, reward)`，而需要明确保存：

```text
turn_id
segment_id
user_reaction
local_reward
terminal_reward
tool_observation
action provenance
policy/checkpoint version
```

来源：
- [arXiv：FACA](https://arxiv.org/abs/2608.17499)

## 6. Agent Sandbox / Runtime / Infra

### 6.1 Sandbox 已经从“隔离容器”变成“Agent Control Runtime”

今天三组独立信息指向同一个方向：

- OpenAI 的前沿 Agent 安全事件要求更严格的 **isolated environment + restricted network/tool + monitoring + sandboxed execution**；
- Guidelight 把 **critical action boundary / fail closed / tamper-evident logs** 写成具体控制原则；
- PACE 则用一个独立 deterministic verifier 演示了“模型动作必须在执行边界再次授权”。

因此更完整的 Agent Runtime 可以抽象成：

```text
Agent / Harness
      ↓
Action Proposal
      ↓
Policy / Risk Gate
      ↓
Credential & Secret Broker
      ↓
Sandbox Runtime
      ↓
Network / Filesystem / Tool / Browser
      ↓
Audit + Monitor + Kill / Rollback
```

这比“起一个 Firecracker/Kata/Container”高了一层。虚拟化解决的是 isolation primitive；Agent Runtime 还要解决 **谁能做什么、什么时候能做、动作是否经过审批、如何回收权限、如何证明执行链没有被篡改**。

来源：
- [OpenAI：Responding to the next frontier of critical cyber capabilities](https://openai.com/index/responding-next-frontier-critical-cyber-capabilities/)
- [Guidelight：Control](https://guidelight.ai/control)
- [PACE](https://arxiv.org/abs/2608.17220)

### 6.2 PACE 的“Policy Decision Record”值得 Sandbox 平台借鉴

**日期：2026-08-18。**

PACE 把 verifier 的判断签名成 Policy Decision Record，并绑定具体执行 bytes。对普通 Agent Infra 可以类比为：

```text
agent action
+ tool identity
+ args hash
+ tenant/session
+ policy version
+ secret scope
+ timestamp/TTL
+ sandbox identity
→ signed/immutable decision record
```

这样能避免“审批的是 A，最后执行的是 B”，也方便事后审计。它不意味着所有 Agent Runtime 都要做密码学签名，但 **decision 与 actual execution 强绑定** 是很值得吸收的设计原则。

来源：
- [arXiv：PACE](https://arxiv.org/abs/2608.17220)

## 9. 对技术路线与职业方向的影响

### 9.1 今天最值得深入学习的 3 个技术点

**第一：Train-Inference Consistency / Harness-Native RL。**  
不要只理解 PPO/GRPO 公式，重点研究真实 Harness 中的 context compaction、tool message、retry、reserialization 之后，trainer 如何准确恢复 policy token 和 log-prob。LEGO-RL 是非常好的切口。

**第二：Agent Runtime 的 Action Boundary。**  
把 Sandbox 从“资源隔离”提升为“执行控制”：tool 权限、secret scope、network egress、policy gate、audit、kill switch、TTL、fail-closed。这一层会同时服务 production Agent 和 RL environment。

**第三：Trajectory / Reward Data Model。**  
FACA 说明 multi-turn RL 以后会需要更细粒度的局部反馈。Trajectory service 应该天然支持 turn/segment/action/tool-observation/reward provenance/checkpoint version，而不是只存一整个 JSON transcript。

### 9.2 可能形成岗位机会的趋势

今天的信号进一步支持几类岗位：

- **Agentic RL Infra / Rollout Platform**：真实 Harness 接入、异步 rollout、trajectory、reward/verifier、训练推理解耦；
- **Agent Runtime / Sandbox Platform**：隔离、权限、network/secret、执行审计、environment lifecycle；
- **Coding Agent Infrastructure**：repo environment、workspace、tool harness、test/eval、long-running task orchestration；
- **Inference Systems**：KV cache、memory disaggregation、PD、networking、custom accelerator system integration。

相对而言，单纯“再封装一个 Agent Workflow SDK”或者“只做 MCP tool registry”更容易同质化，除非它同时掌握 execution、state、security 或 training 闭环。

### 9.3 哪些更像短期热点

- 没有一手资料的下一代模型代号竞猜；
- 只靠 prompt 组合出来的“多 Agent 架构”；
- 把一个普通容器 API 换名叫“Agent Sandbox”，但没有 snapshot、network policy、secret、audit、multi-tenancy、lifecycle；
- 单纯把 GRPO 接上 tool call，却没有解决真实 Harness 的 token 对齐、环境稳定性和 reward provenance。

### 9.4 今天可以执行的一个实践

**做一个最小的 Harness-Native Rollout PoC，而不是再做一个完整平台。**

建议只验证下面这条链路：

```text
Coding Agent Harness
    ↓
LLM Proxy（记录 request / raw generation / model version）
    ↓
Sandbox（执行 shell / tests）
    ↓
Trajectory Recorder
    ↓
Verifier / Reward
    ↓
离线重算 token / logprob 或做一致性检查
```

目标不是马上训练模型，而是先回答三个工程问题：

1. Harness 做 context compaction 后，能否准确知道哪些 token 真正来自当前 policy？
2. Sandbox crash / timeout / retry 后，trajectory 怎样保持可恢复和可审计？
3. Reward 能否和具体 action、test result、environment state 精确绑定？

如果这三件事能打通，就已经踩到了 **Agentic RL Infra + Sandbox + Agent Runtime** 的真实交叉点，比做一个普通 Agent Demo 更有技术含量。

## 今日结论

今天的信息可以压成一句：

> **Agent 竞争正在从“模型会不会调用工具”，进入“真实 Harness 能不能训练、执行环境能不能控制、动作能不能审计、基础设施能不能支撑长时间高并发运行”的阶段。**

LEGO-RL 是训练侧最值得关注的新信号；OpenAI/Guidelight/PACE 共同强化了 Runtime 控制边界的重要性；Google-Marvell 则提醒我们，Agent workload 最终仍要落在一整套 compute-memory-network-storage 系统上。对 AI Infra 来说，这些变化比今天有没有新模型登顶某个 benchmark 更值得跟踪。
