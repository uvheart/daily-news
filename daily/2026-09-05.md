#### 2. Anthropic 完成费马大定理首个完整计算机验证形式化：多 Agent + Verifier 路线出现标志性案例

- **日期：2026-09-04**
- Anthropic 公布费马大定理（FLT）的首个完整 computer-checked formalization。Claude 在约 11 天中大规模自主工作，最终证明由 Lean 检查；Anthropic 披露整个过程产生了约 1,300 万行 Lean，中间证明约 29,500 个 theorem，并使用大量 Claude Agent 协作。
- 一个关键工程点是 **Prove2Me 使用 DAG 管理 theorem dependency**，将大问题拆成可验证子问题，并借助 Lean 充当强 verifier，降低长周期 Agent 的记忆衰减和错误累积。
- **为什么重要**：这是“Agent Harness + 多 Agent 编排 + 自动 verifier + 长任务状态管理”在科学研究上的高价值展示，和 Agentic RL 中 environment/reward/verifier 的工程问题高度同构。
- 来源：[Anthropic：Formalizing Fermat's Last Theorem](https://www.anthropic.com/research/formalizing-fermats-last-theorem)

### 【与用户最相关的 3 个信号】

#### 信号 1：Agent Runtime 正在变成“AI 时代的执行控制面”

模型负责决策，但真正需要工程化的是 **谁允许 Agent 执行什么、在哪个隔离域执行、能访问哪些网络和 Secret、任务何时回收、发生异常如何暂停/撤销、完整 trajectory 如何审计**。Astra 的安全设计和近期 Agent 事故都说明，Sandbox 不再只是“给 Coding Agent 一个容器”，而会逐步演化成完整的 Agent Runtime Control Plane。

#### 信号 2：Agentic RL 的瓶颈正在从算法 API 转向 Environment 生命周期正确性

AReaL 的 port/process owner 修复非常有代表性：rollout 数量上千以后，真正导致吞吐下降和训练不稳定的经常是 **环境泄漏、worker 卡死、失败重试不幂等、旧 generation 误回收新资源、环境状态无法 replay**。Environment-as-a-Service 的价值会越来越高。

#### 信号 3：训练、采样、推理正在进一步“系统合流”

vLLM/SGLang 的同步点、H2D、CUDA Graph、MLA prefill 优化，看起来属于 serving，但对 RL rollout 同样关键。未来 Agentic RL Infra 不太可能只懂 Ray / PPO 编排，还必须理解 **推理引擎、KV/Prefix Cache、权重同步、prefill/decode、accelerator kernel 和异步资源调度**。

- **发布日期：2026-09-04**

  5. **Failure localization**：错误被限制在局部 theorem，而不是污染整个任务。
- **为什么重要**：Agentic RL 很多问题也可以用同一架构理解——task → environment → trajectory → verifier/reward → retry/branch → artifact。

## 6. Agent Sandbox / Runtime / Infra

这一部分今天反而是最应该关注的。

### 从近期事件反推一个 Agent Runtime 最小能力集合

OpenAI Astra 的官方安全设计、Reuters 报道的 Agent 事件，以及 Cursor/Daytona 的执行环境解耦，基本已经勾勒出未来 Agent Runtime 的控制面：

1. **Identity / Ownership**：每个 Agent、Session、Environment、Worker 都必须有稳定身份和 generation；
2. **Isolation**：container 只是起点，高风险场景需要 VM / microVM / Kata / gVisor 等更强边界；
3. **Network Policy**：默认 deny egress，域名/API allowlist，敏感目标独立审批；
4. **Secret Capability**：短期 token、按 tool / resource scope 授权，不把长期 credential 直接放进环境；
5. **Lifecycle**：create → ready → exec → reset → snapshot → suspend → resume → destroy 明确状态机；
6. **Trajectory Audit**：模型 reasoning、tool call、shell、文件变化、网络请求关联到同一 trace；
7. **Kill / Revoke**：异常时不只是停止 LLM generation，还要撤销 token、杀 worker、断网络、冻结 workspace；
8. **Replay / Forensics**：能重放环境版本、输入、工具版本和 Agent trajectory，方便 reward/debug/事故调查。

### 与 Kubernetes 的连接

Kubernetes 社区今年已经把 Agent Sandbox 抽象为独立 workload primitive，强调 singleton stateful sandbox、稳定网络身份、warm pool、claim、suspend/resume，并可组合 gVisor/Kata 等隔离。这不是今天的新发布，但在今天的新闻背景下更值得重看：**Agent Runtime 很可能会复制 Pod/VM 的演化路径——从“起一个容器”逐步发展成有独立 API、调度、配额、安全和生命周期语义的基础设施对象。**

- 背景资料（2026-03-20）：[Kubernetes：Running Agents on Kubernetes with Agent Sandbox](https://kubernetes.io/blog/2026/03/20/running-agents-on-kubernetes-with-agent-sandbox/)
- 当前案例（2026-09-02）：[Daytona × Cursor Self-Hosted Machines](https://www.daytona.io/dotfiles/cursor-self-hosted-machines-on-daytona)

### 今天应如何理解这些 Infra 更新

**不要只把 vLLM / SGLang 当“在线推理框架”，也不要只把 AReaL / verl 当“RL 框架”。** 在 Agentic RL 中，rollout 本身就是大规模在线 serving workload；而训练侧又需要不断把权重推回 inference engine。最终系统会围绕以下闭环收敛：

`Environment → Agent Rollout → Trajectory → Reward/Verifier → Buffer → Training → Weight Update → Inference Engine → Environment`

其中任意一段的尾延迟、资源泄漏或 correctness bug 都会拖垮整个闭环。

## 9. 对用户职业与技术路线的影响

### 最值得深入学习的 3 个技术点

#### 1. Agent Runtime Control Plane

比再写一个 Agent Framework 更值得投入。建议系统理解：

- Sandbox API / CRD 设计；
- lease、owner、generation、TTL；
- Kata / gVisor / Firecracker / container 隔离差异；
- Secret / NetworkPolicy / egress proxy；
- snapshot / suspend / resume / reset；
- audit / trajectory / kill switch。

**岗位价值**：这类能力同时服务 Coding Agent、Computer Use、Browser Agent、Agentic RL、企业私有 Agent，复用面非常广。

#### 2. Environment + Trajectory 的可重放语义

Agentic RL 往后做大，真正稀缺的不是“能调 GRPO”，而是：

- 同一个 task 能否 reset 到完全一致的环境；
- 环境镜像、依赖、tool version 能否 pin；
- trajectory 能否带完整 observation/action/tool-result；
- 失败 rollout 能否定位到模型、environment 还是 infra；
- reward/verifier 是否可重新计算；
- rollout / training 异步后如何处理 staleness。

这部分正好连接 **云原生控制面 + RL 数据面**。

#### 3. Serving Critical Path

至少把这些概念吃透：

`continuous batching / prefill-decode / KV & prefix cache / CUDA Graph / H2D-D2H / pinned memory / weight update / disaggregated inference / MLA / MoE EP`。

今天 vLLM/SGLang 的提交再次说明：Agentic RL 平台最终会被 inference engine 的行为深刻影响。

### 可能形成岗位机会的趋势

1. **Agent Runtime / Sandbox Platform Engineer**：企业 Agent 大规模落地后必需；
2. **Agentic RL Systems / Environment Platform**：负责 environment、rollout、trajectory、reward 和资源调度，而非只做算法；
3. **Inference + RL 一体化 Infra**：懂 vLLM/SGLang，又懂训练/权重同步/异步 rollout 的工程师会比单一 serving 或单一训练框架更稀缺；
4. **AI4Science Platform**：模型之外，需要科研数据、工具执行、verifier、集群和 reproducibility 基础设施。

### 哪些更可能只是短期热点

- 单纯围绕某个 benchmark 做 prompt / harness tweak、无法迁移到真实 workload 的优化；
- 没有 isolation / state / observability 的薄 Agent Wrapper；
- 只会调用某一个 RL 框架 API，而不理解 rollout、inference 和 distributed lifecycle 的“平台开发”。

### 一个可执行的实践建议

做一个小型 **Environment-as-a-Service / Agent Sandbox Control Plane**，而不是再写一个聊天 Agent：

```text
POST /environments
POST /environments/{id}/exec
POST /environments/{id}/reset
POST /environments/{id}/snapshot
POST /environments/{id}/suspend
POST /environments/{id}/resume
DELETE /environments/{id}
```

底层用 Kubernetes Controller 管理 `AgentEnvironment`：

- 每个 Env 带 `environment_id + generation`；
- 支持普通 Pod 与 Kata/gVisor 两种 runtime class；
- 默认 deny egress，通过 policy 显式开放；
- Secret 用短期 token 注入；
- workspace 支持 snapshot/reset；
- 用 Lease/TTL 自动清理；
- 完整记录 exec/tool/network trajectory；
- create/reset/delete 全部做幂等；
- 加上 cold-start P50/P95、reset P95、环境失败率、orphan 数、每 1k trajectories 成本等指标。

然后接一个 Coding Agent 或简单 Agentic RL rollout worker，把 **Env 创建 → 执行 → trajectory → verifier → reset → 回收**完整跑通。

这类项目能同时证明 Kubernetes 控制面、分布式生命周期、Agent Runtime、Sandbox 和 Agentic RL 的能力，比单独做一个“Agent Demo”更接近未来两三年 AI Infra 岗位真正会买单的东西。

## 今日结论

**2026-09-05 最值得记住的不是某个模型又高了几个点，而是 Agent 系统的工程重心正在明显下沉到 Runtime。**

模型会越来越能执行；因此 **Sandbox、Environment、权限、生命周期、trajectory、verifier、资源调度和推理系统**的重要性只会上升。Anthropic FLT 展示了“多 Agent + Verifier + 持久化编排”能把任务规模推到过去难以想象的长度；AReaL、vLLM、SGLang 的更新则提醒我们，大规模 Agent/RL 最终仍然要落回最传统也最难的系统问题：**状态、资源、并发、失败恢复和性能关键路径。**
