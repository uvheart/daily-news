#### 4. RISE：不依赖外部 Teacher，用 RLVR 自身轨迹“外推”出持续变强的 On-Policy Teacher

- **公开批次：2026-09-07；arXiv v1：2026-09-04 UTC**
- Salesforce AI Research 提出 RISE（Recursive Improvement via Self-Extrapolating Policy Distillation）：通过当前 checkpoint 与 trailing anchor 的参数/输出 logit 位移，构造 synthetic teacher，把 RLVR 的稀疏 outcome reward 转换为 dense token-level target。
- Teacher 随 student 每轮刷新，使 OPD 从一次性压缩变成递归改进机制；论文在数学、STEM、代码和 multi-turn agent 任务上都报告优于 RLVR-only 与普通 self-distillation。
- **为什么重要**：如果方法能够稳定扩展，Agentic RL 的训练栈会出现新的状态：**Rollout 不只产 reward / trajectory，还能决定下一轮 teacher；teacher 本身成为训练循环中的动态对象。**
- 来源：[arXiv — RISE](https://arxiv.org/abs/2609.05295)

#### 7. verl 修复 Fully-Async + MoE 的 R2 Router Replay：异步 RL 正确性开始深入到“路由状态”

- **日期：2026-09-07（merged）**
- verl 合入 PR #7106，修复 Megatron 下 THD-packed batch 的 **R2 router replay correctness**：需要把计算 old log-prob 时使用的 MoE route 记录下来，并在 actor update 时重放；sequence-parallel alignment padding、PP/VPP 本地 router 索引都可能导致 replay 对错层或错 token。
- PR 同时强调这条路径会用于可选的 fully-async rollout 配置。
- **为什么重要**：Agentic RL 的“版本一致性”已经不仅是 model weight version。对于 MoE + async rollout，**router decision、old log-prob、trajectory、actor version、packed sequence layout** 都可能成为训练正确性的状态。

#### 8. Agent Memory 迁移研究：模型升级后，Memory Store 不变不代表“记忆还在”

- **公开批次：2026-09-07；arXiv v1：2026-09-04 UTC**
- 一项受控实验比较 LC-RAW、RAG、自然语言 NOTES 与固定 Schema KG 的迁移稳定性。固定 schema KG 在 writer model 更换后几乎不变（+0.0004 ± 0.0020），而自然语言 NOTES 对模型迁移方向高度敏感；RAG 如果只迁一半 embedding index，也会损失大部分收益。
- 论文还发现，仅保留压缩后的 NOTES 很难恢复；保留 raw source history 能明显提高 repair 成功率。
- **为什么重要**：长期 Agent Memory 不应该只是“一个向量库”。生产系统需要 **memory schema version、embedding version、writer/reader model version、raw evidence retention、migration job 与 rollback**。
- 来源：[arXiv — Does Your Agent's Memory Survive a Model Upgrade?](https://arxiv.org/abs/2609.05339)

### 【与用户最相关的 3 个信号】

#### 信号 1：Environment 正从“启动一个 Sandbox”升级成 Agent Data Plane

CUA-Universe 最值得注意的不是 GUI+CLI 本身，而是它把环境变成：

**Environment Build → Snapshot/VM → Interface Discovery → Task Generation → Rollout → Verification → Trajectory → Post-training**。

这意味着 Environment-as-a-Service 的高价值方向不只是 `create/reset/delete` API，而是继续补上 **artifact/version、dataset binding、network/secret policy、observation/action protocol、checkpoint、verifier、trajectory lineage 和 replayability**。

#### 信号 2：Agentic RL Infra 下一阶段拼的是“状态一致性”，不是简单吞吐

今天 verl 的 router replay、TRL 的 async GRPO weight-transfer dependency、vLLM 的 fine-tuned checkpoint 兼容性都在说明同一件事：

**Trainer / Rollout / Serving / Model Checkpoint / Router / KV / Weight Transfer** 之间只要有一个版本或语义错位，训练可以“正常跑完但结果不对”。

因此，比单纯做一个高 QPS rollout server 更值钱的能力是：**versioned rollout、weight epoch、trajectory provenance、idempotent update、barrier/handshake、recovery 与 correctness observability**。

#### 信号 3：Agent 的长期状态需要像数据库 Schema 一样治理

Memory portability 论文给出了一个非常工程化的结论：自由文本 NOTES 很容易绑定 writer model；RAG embedding 迁移不能新旧混用；fixed-schema representation 更稳定；原始证据最好保留。

对生产 Agent，Memory 应至少有：**source/raw log → normalized memory → embedding index → derived summary** 四层，并且每层都可标记版本、重建、迁移和回滚。

### 4. Agent / Coding Agent / Computer Use

#### 4.1 CUA-Universe：GUI 与 CLI 不应被当成两套孤立 Agent

- **公开批次：2026-09-07；v1：2026-09-04 UTC**
- 真实桌面工作往往是 hybrid：视觉用于读取状态，CLI 用于高吞吐、精确操作。CUA-Universe 的核心贡献是让两种接口共享同一应用状态，并自动生成混合任务与 verified trajectory。
- **对 Computer Use 的启示**：未来 Computer-use Runtime 很可能需要统一暴露 **screen/DOM/accessibility tree + terminal + filesystem + application API**，而不是把 GUI Agent 与 Coding Agent 分成完全不同的产品。
- 来源：[arXiv](https://arxiv.org/abs/2609.05374)

#### 4.2 Agent Memory：升级模型前要先问“Memory 是谁写的、谁读的、Embedding 是哪一版”

- **公开批次：2026-09-07；v1：2026-09-04 UTC**
- 固定 schema memory 比自然语言压缩 notes 更容易跨模型迁移；混用新旧 embedding index 会明显损失 retrieval gain；保留 raw history 能显著提高 repair 能力。
- **工程建议**：长期记忆应像数据库一样有 schema/version/migration，而不是直接把 `summary + vector` 当永恒真相。
- 来源：[arXiv](https://arxiv.org/abs/2609.05339)

#### 4.3 Qwen Code：Workflow、IPC、Daemon、Session Projection 成为 Harness 一等对象

- **日期：2026-09-07**
- Qwen Code preview.2 延续了 workflow run management、IPC refusal/expiry、daemon verification checkpoint 等设计。
- **判断**：Agent Harness 正快速重演分布式系统已经解决过的问题：状态机、幂等、backpressure、message ownership、lease、cancellation、durable history。
- 来源：[Qwen Code release](https://github.com/QwenLM/qwen-code/releases/tag/v0.23.1-preview.2)

### 5. Agentic RL / RL Infra

#### 5.1 verl R2 Router Replay：MoE route 也属于“训练轨迹状态”

- **日期：2026-09-07**
- 对 asynchronous / packed MoE RL，计算 old log-prob 时走过的 route 如果在 actor update 阶段无法准确 replay，importance ratio 等训练量就可能失真。
- 修复涉及 THD alignment padding、PP/VPP-local router instance、replay tensor shape 与缺失数据 fail-fast。
- 来源：[verl PR #7106](https://github.com/verl-project/verl/pull/7106)

#### 5.2 TRL Async GRPO：默认 Weight Transfer 明确依赖 vLLM >= 0.22.0，并改为初始化前 Fail Fast

- **日期：2026-09-07（merged）**
- TRL PR #6830 修复一个很典型的 Infra UX：默认 `WeightTransferClient` 需要 `vllm>=0.22.0`，但旧逻辑会在 model load、Flash Attention 初始化之后才报错；现在在 AsyncGRPOTrainer 初始化开头就检查依赖。
- **核心技术点**：Async RL 训练框架已经把 **weight transfer backend** 作为显式可替换组件，而不是 trainer 内部细节。
- **为什么重要**：随着 rollout 与 trainer 解耦，weight transport 的 protocol/version/compatibility 会变成标准接口问题。
- 来源：[TRL PR #6830](https://github.com/huggingface/trl/pull/6830)

#### 5.3 On-Policy Distillation：数据量可能远没有“难样本长度”重要

- **公开批次：2026-09-07；v1：2026-09-04 UTC**
- 《What Matters in On-Policy Distillation?》报告：1-shot OPD 在不同样本上都能有效，hard examples 往往提升更大；主要驱动力不是 token entropy，而是 hard problem 产生的更长 CoT。作者进一步报告，4 个 1.5B–7B 模型上仅 8 个筛选后的 hard examples 可以匹配 17K dataset baseline。
- **判断**：如果结果能被更多实验复现，后训练数据工程会进一步从“大量生成”转向 **difficulty-aware selection + long reasoning trajectory quality**。
- 来源：[arXiv](https://arxiv.org/abs/2609.05198)

#### 5.4 RISE：把 RL trajectory 变成动态 Teacher

- **公开批次：2026-09-07；v1：2026-09-04 UTC**
- RISE 将 RLVR 的 checkpoint displacement 外推出 synthetic teacher，并每轮刷新。
- 对 Infra 的潜在新需求包括：anchor checkpoint 生命周期、teacher/student version binding、logit/parameter extrapolation、on-policy sampling 与 distillation 任务共调度。
- 来源：[arXiv](https://arxiv.org/abs/2609.05295)

### 6. Agent Sandbox / Runtime / Infra

#### 6.1 Agent Runtime 必须支持 Forensics，而不仅是 Isolation

OpenAI 事故进入欧盟报告流程后，Sandbox 的“安全”定义会继续扩展：

**Isolation → Egress Policy → Credential Mediation → Action Audit → Artifact Snapshot → Session Replay → Incident Kill/Revocation → Forensic Export**。

只做到 Firecracker/Kata 隔离仍然不够；生产 Agent 平台最终需要像云平台一样提供 workload identity、policy、日志与审计面。

- 来源：[Reuters — OpenAI EU incident report](https://www.reuters.com/business/openai-has-sent-eu-incident-report-hijacked-german-website-commission-says-2026-09-07/)

#### 6.2 CUA-Universe 给 Environment-as-a-Service 一个更完整的抽象

环境不是“一个容器/VM”，而是 **image + app state + interfaces + task contract + reset semantics + verifier + artifacts**。如果把它映射成平台，可以设计成：

`EnvironmentSpec -> Provision -> BindTask -> RunSession -> Snapshot -> Verify -> ExportTrajectory -> Reset/Destroy`

- 来源：[CUA-Universe](https://arxiv.org/abs/2609.05374)

#### 6.3 Substrate-Aware Agent：把 RAM/时间预算直接告诉 Agent，会改变它生成的程序结构

- **公开批次：2026-09-07；v1：2026-09-04 UTC**
- 这是一篇单作者、小规模 controlled study，应谨慎看待，但结论很适合 Runtime：向 Agent 明确提供 `128 MB RAM + 10s wall-time` 等 execution contract 后，模型会主动使用 bounded blocking、float32、memory mapping 等结构；论文报告 peak memory 与 wall time 显著下降。
- **启示**：Environment API 不只应该把“工具”给模型，也可以把 **resource contract / quota / timeout / network availability / accelerator type** 作为 planning context。
- 来源：[arXiv — Substrate-Aware AI Agents](https://arxiv.org/abs/2609.05232)

> **Firecracker / Kata / Kubernetes**：在本次 24–48 小时窗口内，没有找到足够高信号、值得单列的官方重大 release；今天更值得关注的是上层 Agent Runtime 如何把 sandbox/VM 变成可验证、可迁移、可审计的 execution environment。

### 9. 对用户职业与技术路线的影响

#### 今天最值得深入学习的 3 个技术点

**1. Versioned Agent Environment / Runtime Contract**

不要只研究“怎么起 Kata/Firecracker”。进一步看：

- `EnvironmentSpec` / image / snapshot 如何版本化；
- task 与 environment 如何绑定；
- resource/network/secret contract 如何下发；
- rollout 产生的 filesystem diff、tool trace、artifact、reward 如何归档；
- 如何 reset、resume、replay、forensics。

CUA-Universe 与 OpenAI incident 两条线合起来，正好说明未来的 Sandbox 平台会同时承担 **数据生产面 + 安全控制面**。

**2. Async RL 的 Correctness Plane**

今天 verl / TRL / vLLM 最应该连起来看：

`checkpoint version -> weight transport -> rollout engine -> MoE route / old log-prob -> trajectory -> actor update -> serving reload`

任何一环的版本或 shape 不一致，都可能不是“报错”，而是 silent correctness bug。未来 Agentic RL Infra 工程师的核心竞争力之一，会是能设计 **version / epoch / lineage / barrier / handshake / recovery**。

**3. Memory / State Migration**

Agent 的 session、memory、embedding、workflow projection 都在快速迭代。Qwen Code、DeepSeek Harness 的近期工程问题以及 Memory portability 论文都说明：**durable state 是 Harness 最难的部分之一。**

值得系统补：event sourcing、schema evolution、snapshot + WAL、projection rebuild、idempotency、migration/rollback。这些传统后端/云原生能力会直接迁移到 Agent Runtime。

#### 可能形成岗位机会的趋势

- **Agent Runtime / Execution Platform**：Sandbox、credential、network、artifact、audit、replay、kill/revoke。
- **Agentic RL Data Plane**：rollout、environment、trajectory、reward/verifier、weight transport、async/off-policy consistency。
- **AI-for-AI Platform**：自动实验编排、可验证搜索、experiment DAG、资源调度、结果 lineage。
- **Heterogeneous AI Infra**：CUDA + ROCm + Ascend/NPU 多硬件上的训练/serving consistency。

这些方向比“再做一个 Agent SDK wrapper”更有壁垒，也更适合云原生/后端平台型工程能力。

#### 哪些更像短期热点

- 单纯围绕某个 frontier model 的 prompt/harness 参数调优；
- 没有 verifier / evaluation 的 multi-agent demo；
- 只强调 benchmark 峰值、但没有 runtime cost、failure rate、state recovery 的 Agent 产品；
- 仅靠“套一个 Kubernetes Job”就称为 Agent Sandbox 平台。

#### 一个可执行的学习 / 实践建议

本周可以做一个很小但很有价值的 **`EnvRun` PoC**，不要再做通用 Agent 框架：

1. 定义一个 `EnvironmentSpec`：image、CPU/GPU、RAM、timeout、network policy、secret references；
2. `CreateRun` 返回 `run_id + env_version + lease`；
3. Agent 在 sandbox 中同时获得 terminal + filesystem + 一个简单 GUI/VNC/CDP channel；
4. 每个 action 写入 append-only event log；
5. 结束后输出 `artifact manifest + trajectory + resource metrics + verifier result`；
6. 支持 `replay(run_id)` 和 `fork(run_id, event_seq)`；
7. 最后再接一个简单 GRPO/rollout client，而不是一开始就碰训练框架。

这个 PoC 能把今天最重要的三条主线一次串起来：**Environment-as-a-Service、Agent Runtime 可审计性、Agentic RL Trajectory Data Plane**。
