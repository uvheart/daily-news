### 【与用户最相关的 3 个信号】

1. **Sandbox 的核心正在从 VM/container backend 转向 Capability Control Plane。**  
   Firecracker、Kata、container、bwrap 都只是执行后端；真正长期有平台价值的层是 `Identity + Session + Lease + FilesystemPolicy + NetworkPolicy + CredentialBroker + Audit + Kill/Resume`。GitHub Copilot 今天的 local sandbox policy 是一个非常具体的产业验证。

2. **Stateful Runtime 会成为 Agent Infra / Environment-as-a-Service 的下一层壁垒。**  
   Google 的 persistent private memory、RBG 的 Stateful rollout recovery、vLLM-Omni 的 connector/KV state reclamation其实都在解决同一类问题：一个任务跨请求、跨 Worker、跨设备之后，谁拥有状态，状态如何恢复，旧 owner 如何失效，资源如何最终回收。

3. **Agentic RL 的“训练-采样一致性”已经成为独立 Infra 问题。**  
   verl 的 score centering 和 vLLM layerwise weight reload 都指向一个事实：trainer 与 rollout engine 不完全同步时，quantization、stale weight、kernel layout 都会让算法语义漂移。未来 RL Infra 的平台能力应该显式提供 `weight version / rollout version / sampler logprob / trajectory lineage / verifier version`，而不是把这些藏在训练脚本里。

## 5. Agentic RL / RL Infra

### 5.1 verl：为 training-inference mismatch 引入 score centering

- **日期：** 2026-09-23
- **状态：** Draft PR，尚未正式合入
- **摘要：** verl PR #8010 为 bypass-mode REINFORCE 增加 score centering。PR 解释，在 trainer 与 sampler 存在 mismatch 时（例如 sampler stale/quantized），policy gradient 会出现把 trainer 朝 sampler 蒸馏的 drift term；score centering 用 sampler 下的 expected score 做无超参修正，并可与 token-level importance sampling 等机制组合。
- **核心技术点：** rollout 返回 sampler top-k log-probs、score centering、token-level TIS、training-inference mismatch correction。
- **为什么重要：** RL Infra 不能只保证“拿到 trajectory”，还要保存足够的 sampler-side statistics 和 version metadata，让训练端知道 trajectory 是在什么 policy/quantization/kernel 下产生的。
- **来源：** [verl PR #8010](https://github.com/verl-project/verl/pull/8010)

### 5.2 verl：标准 vLLM weight sync 进入 layerwise reload lifecycle

- **日期：** 2026-09-22
- **状态：** Open PR
- **摘要：** PR #7987 修复标准非量化 vLLM weight sync 对 MoE kernel checkpoint layout 的隐含依赖，将权重同步放进 vLLM 自己的 layerwise reload lifecycle。
- **核心技术点：** weight reload lifecycle、MoE kernel layout、trainer → rollout engine live weight sync。
- **为什么重要：** Online RL / colocated training-serving 中，“权重同步成功”不等于 tensor copy 成功；还必须尊重 serving kernel 的 layout 与 reload 生命周期。
- **来源：** [verl PR #7987](https://github.com/verl-project/verl/pull/7987)

## 6. Agent Sandbox / Runtime / Infra

### 6.1 Sandbox：从 Isolation Backend 进入 Capability Control Plane

今天 GitHub 的 local sandbox 是最明确的产业信号。一个可泛化的 Agent Runtime API 应该至少覆盖：

```text
Session
├── Identity / Principal
├── Lease / Generation
├── Filesystem Capability
├── Network/Egress Capability
├── Credential Lease
├── Tool/Process Capability
├── Artifact / StateRef
├── Audit Log
├── Snapshot / Resume
└── Kill / Revoke
```

后端可以是 container、Kata、Firecracker、VM 或本机受限执行；控制面不应该让业务方感知每个 backend 的权限实现细节。

来源：[GitHub Copilot Local Sandboxing](https://github.blog/changelog/2026-09-23-local-sandboxing-in-the-github-copilot-app/)

### 6.2 Memory：从应用数据库升级为 Runtime State Plane

Google Private AI Compute 的方向可以抽象成：

`Device Identity -> Key -> Encrypted Persistent State -> Attested Enclave -> Inference -> Re-encrypt -> Cross-device Resume`

这与普通 Redis/Vector DB 最大的区别是：**状态访问权属于用户/Session 身份，而不是某个长驻 server process。** 对企业 Agent，类似思想可以延伸到短期 credential、MCP secret、browser cookie、workspace snapshot 与长期 memory。

来源：[Google DeepMind Private AI Compute](https://deepmind.google/blog/advancing-private-ai-compute-with-secure-server-side-memory/)

- **日期：** 2026-09-23
- **状态：** Draft PR

## 9. 对用户职业与技术路线的影响

### 9.1 今天最值得深入学习的 3 个技术点

**第一：Capability Control Plane。**  
不要把 Sandbox 学成“Firecracker 怎么起 VM”。更值得掌握的是：如何定义统一 Capability Schema，再分别映射到 K8s Pod/Kata/Firecracker/local sandbox；如何做 credential lease、network egress、FS mount、audit 和 revoke。

**第二：Stateful Agent Runtime。**  
把 Agent Session 当成一个分布式系统实体：`session_id + owner + generation + lease + state_ref + artifact_ref + capability + checkpoint`。重点研究 takeover、fencing、resume、idempotency 和 final cleanup，而不是只做 create/delete sandbox。

**第三：RL 的 Training-Sampling Consistency。**  
verl 今天的两个 PR 值得连起来看：一个解决 sampler/trainer mismatch 的算法修正，一个解决 weight reload lifecycle。真正的平台应该给每条 trajectory 自动附带 `policy_version / rollout_engine_version / sampler_logprob / quantization / kernel_version / env_version / reward_version`。

### 9.2 可能形成岗位机会的趋势

最值得押注的不是“某一种 Sandbox 技术”，而是三类平台岗位：

- **Agent Runtime / Environment Platform：** Session、Sandbox、Credential、Policy、Memory、Artifact、Resume。
- **Agentic RL Infra：** rollout、trajectory data plane、weight sync、verifier/reward service、dynamic sampling、failure recovery。
- **AI-for-AI Experiment Platform：** 大规模 Agent Fleet、实验环境、自动评测、artifact lineage、自动回滚与资源调度。

这三类方向共用大量能力，也与 Kubernetes/云原生/分布式系统背景高度兼容。

### 9.3 哪些更像短期热点

- 单纯包装“多 Agent 协作”的 UI/Demo；
- 只比较 Firecracker/Kata/container 启动耗时、却没有 Session/Policy/State 语义的 Sandbox Demo；
- 没有 end-to-end task success/cost 数据，只报模型 benchmark 的 Agent 产品；
- 把普通 RAG memory 换个名字称为“长期 Agent Memory”，却不处理 identity、retention、privacy 和跨 Session 生命周期。

### 9.4 一个可执行的实践建议：做 `Stateful Agent Runtime Gateway v0.1`

用 Kubernetes + 一个轻量控制面做一个可以真实演示的原型：

```text
POST /sessions
POST /sessions/{id}/lease
POST /sessions/{id}/exec
POST /sessions/{id}/credentials
POST /sessions/{id}/snapshot
POST /sessions/{id}/resume
DELETE /sessions/{id}
```

每个 Session 至少带：

```yaml
session_id: xxx
owner: worker-a
generation: 7
lease_expire_at: ...
runtime: kata|container|firecracker
capability:
  fs: ...
  egress: ...
  credentials: ...
state_ref: ...
artifact_ref: ...
```

然后专门做三个 chaos case：

1. Worker A 持有 lease 时宕机，Worker B takeover；A 恢复后因为 generation fencing 无法再次产生副作用。
2. Agent 执行中用户取消，确认 process、network connection、credential lease、KV/connector state 和 artifact writer 全部完成最终回收。
3. Session snapshot 后换节点 resume，保持 StateRef/Artifact 连续，但重新签发短期 credential。

如果这个原型做完整，它会比“再实现一个 Sandbox backend”更能证明 Agent Infra / Environment-as-a-Service 的平台设计能力，因为它覆盖的正是今天 GitHub、Google、RBG、vLLM-Omni 这些不同项目正在分别补齐的同一组核心问题。
